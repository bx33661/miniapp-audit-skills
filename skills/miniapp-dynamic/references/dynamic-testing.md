# Dynamic Verification Notes

动态验证不是盲扫。它只回答一个问题：在受控请求下，某个信任边界是否真的失效。

## 假设矩阵

每个待验证发现先写成一行矩阵，再决定是否发送请求。

| 字段 | 内容 |
|---|---|
| Finding | 静态假设或待验证问题 |
| Asset | 方法 + 路径 + 请求体形态 |
| Identity | 匿名 / 用户 A / 用户 B / 管理员 |
| Baseline | 用当前身份访问自己资源的结果 |
| Mutation | 只改变一个变量 |
| Secure behavior | 服务端应有的拒绝或隔离 |
| Evidence | 状态码、响应差异、状态变化 |
| Result | CONFIRMED / INCONCLUSIVE / BLOCKED / FALSE_POSITIVE |

矩阵中没有明确 asset 和 identity 的测试，不应发送。

## 目标身份卡

在测试前记录目标身份，避免把不同环境或版本的结果混在一起。

```json
{
  "appid": "wx...",
  "envVersion": "develop|trial|release",
  "host": "https://...",
  "package_hash": "sha256:...",
  "account": "test-user-a",
  "capture_source": "Reqable|mitmproxy|other",
  "captured_at": "ISO8601"
}
```

生产环境默认只读。测试环境、体验版和开发版也必须记录 appid、版本和账号，不能只靠域名关键字判断。

## Baseline 与多身份

1. 用用户 A 访问 A 自己的资源，确认请求和响应正常。
2. 用用户 A 访问用户 B 的资源，观察是否被拒绝。
3. 用低权限账号访问管理功能，观察是否被拒绝。
4. 用匿名请求访问需要登录的接口，观察是否被拒绝。

Baseline 失败时，不要解释改参结果；先修复抓包、会话或请求构造。

## 结果定义

| 结果 | 含义 |
|---|---|
| CONFIRMED | 受控请求复现了越权、数据泄露、资金或状态变化，且影响明确 |
| INCONCLUSIVE | 请求成功或失败，但无法区分是权限控制、参数错误、WAF、签名还是环境问题 |
| BLOCKED | 缺少账号、签名、网络、权限或测试数据，无法继续 |
| FALSE_POSITIVE | 有足够证据证明原来的静态假设不成立 |

“Payload 没触发”通常只能得到 `INCONCLUSIVE`，不能直接判 `FALSE_POSITIVE`。

## 常见验证模式

### 对象级授权

- 固定方法和请求体，只改对象标识；不要假设参数名一定是 `id` 或 `order_id`。
- 先用 A 的对象做 baseline，再用 B 的对象做对照。
- 证据是 B 的对象数据或操作结果，不是错误页或空数组。

### 功能级授权

- 用普通用户调用管理接口、导出接口、审核接口。
- 观察是否返回数据、执行操作或暴露管理字段。
- 失败时区分 401/403、业务错误、WAF 和路由不存在。

### 状态与资金

- 只改一个状态字段或金额字段，保持其它参数不变。
- 以服务端订单/支付状态为准，不以客户端提示为准。
- 不执行真实支付、退款或结算。

### 重放与竞态

- 先确认单次请求成功，再重复或并发。
- 记录时间窗口、nonce、签名和会话绑定。
- 并发测试必须有限速和停止条件。

### 注入类

SQL/NoSQL/命令注入只作为可选验证，不作为固定 payload 列表。

- 需要明确授权和测试环境。
- 优先使用时间盲注、带外或差异对比，不依赖错误回显。
- 无回显、WAF 拦截、参数化查询都会导致“未触发”，通常是 `INCONCLUSIVE`。

## 证据

每个结果保留：

- 目标身份卡和账号角色。
- 完整请求：方法、URL、头、体、时间和签名相关字段。
- Baseline 与改参响应。
- 服务端状态变化或数据差异。
- 结果状态和残余不确定性。

## 安全边界

- 只测试授权目标和测试账号。
- 默认只读；写操作需要明确批准和可回滚方案。
- 不访问、保留或发布他人数据。
- 不执行真实支付、退款、删除或权限变更。
- 遵守速率限制；出现不稳定、5xx 或真实数据暴露时立即停止。
