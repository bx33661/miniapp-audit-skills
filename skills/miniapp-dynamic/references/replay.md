# Request Replay and Mutation

Replay is a controlled experiment. Change one variable at a time, keep a baseline, and record the exact request and response.

## Request template

Normalize a captured request into a stable structure:

```json
{
  "source": "reqable",
  "captured_at": "2026-11-03T21:21:24+08:00",
  "application": {
    "name": "微信",
    "id": "com.tencent.flue.WeChatAppEx"
  },
  "request": {
    "method": "POST",
    "url": "https://target.example/app/getMyList",
    "headers": {
      "User-Agent": "...",
      "Referer": "https://servicewechat.com/...",
      "Content-Type": "application/x-www-form-urlencoded"
    },
    "body": "sign=...&timestamp=...&userCode=..."
  },
  "volatile_fields": ["sign", "timestamp"],
  "notes": "Remove Host, Content-Length, Connection and Accept-Encoding before replay."
}
```

Store cookies and authorization tokens separately from the template so they can be rotated without editing the body.

## Header handling

- Keep mini program-identifying headers: `User-Agent`, `Referer`, `xweb_xhr`, content type and accept headers.
- Remove hop-by-hop headers: `Host`, `Content-Length`, `Connection`, `Accept-Encoding`.
- Do not add browser headers that the mini program does not send unless the test specifically requires it.
- Preserve header case when the server may distinguish it.

## Baseline

Before mutations:

1. Send the unmodified request.
2. Confirm the expected status and response shape.
3. Record the baseline body, field set and length.
4. If the baseline fails, do not interpret mutation results.

## Mutation matrix

Change one dimension at a time:

| Dimension | Examples | Expected signal |
|---|---|---|
| Object identity | `orderId`, `userId`, `fileId`, `recordId` | Another object's data or unauthorized action |
| Tenant/org | `tenantId`, `unitCode`, `orgId` | Cross-tenant data or scope |
| Role/privilege | `role`, `userType`, `isAdmin` | Protected function accepted |
| Money | `amount`, `price`, `quantity`, `discount` | Total or state inconsistent with server rules |
| State | `status=paid`, `refunded`, `approved` | Illegal transition accepted |
| Method | `GET` to `POST`, `PUT`, `DELETE` | Method-level authorization gap |
| Headers | Remove token, change origin/referer | Authentication or CSRF gap |
| Body shape | Add field, remove field, wrong type | Mass assignment or validation gap |

Use a test account and synthetic identifiers. Do not enumerate real users.

## Response comparison

Compare:

- Status code and error code.
- Top-level keys and nested field presence.
- Record count and identifiers.
- Length or hash of the response body.
- Server-side state, when observable through a separate read.

A different error message is not proof of a vulnerability. A successful unauthorized action, data return or state change is.

## Error classification

| Observation | Interpretation | Next step |
|---|---|---|
| No request reaches the server | Proxy bypass, certificate, or client restriction | Fix capture path |
| TLS or certificate error | CA not trusted or pinning | Trust the CA or investigate pinning |
| 401/403 after a valid baseline | Authorization check exists | Try a different role or object; do not force |
| 200 with an error body | Application-level rejection | Inspect error semantics |
| 200 with different data | Potential authorization or logic failure | Confirm scope and impact |
| Timeout or rate limit | Control exists or test too aggressive | Reduce rate; record limitation |

## Signatures, timestamps and sessions

- Prefer a fresh request generated by the app.
- Identify which fields are volatile and whether they are covered by a signature.
- If a signature covers the tested field, static analysis or a hook is required.
- Do not brute-force signatures or replay at high volume.
- A replay failure may indicate a control, a stale request or an incomplete harness; distinguish these before reporting.

## Evidence

For each mutation, retain:

- The exact request and response.
- The baseline and the changed field.
- The time and account role.
- The observed difference and its security meaning.
- The evidence level and residual uncertainty.

Redact tokens, cookies and personal data.
