# 从真实流量开始测试

只有运行中的小程序、授权目标与测试账号时使用。无需源码、wxapkg 或已有静态发现。已有具体请求或假设时也可从基线步骤开始。

## 1. 确认抓包链路

先核对目标、账号、环境、允许操作和数据规则。仅在已授权范围内配置代理、证书和抓包开关；操作步骤见 `reqable.md`。

记录一次具体动作与时间，例如测试账号打开自己的订单页。先按授权 host 过滤，再按实际应用、方法或路径缩小；读取对应记录，确认 host、请求体、响应和业务动作相符。看到 CONNECT、只有代理连接成功或创建了请求标签，都不代表已读取目标 HTTPS 流量。

Reqable 的 capture_live_filter 返回记录 ID，需再调用 capture_live_get_by_id 读取详情。过滤条件按实际工具 schema 构造；application 与 host 等多个条件按 AND 组合，过度组合可能漏掉 web-view、上传下载或云调用。记录 ID 可跨抓包会话复用，必须连同时间与环境引用。

## 2. 从流量建立业务地图

逐个执行范围内的正常业务动作，记录动作、身份、实际域名/环境、方法、路径、对象/租户标识、认证与签名字段、响应对象和状态。把登录、查询、创建、状态查询等请求按实际先后关联；不凭路径名称猜写操作。

区分微信平台、业务后端、云 SDK、web-view 与其它主体；一个页面可触发多个域名和不同会话。未知主体或不可读载荷保留未知。开发与运行关系需要时读 `../../miniapp-audit/references/runtime-model.md`。

## 3. 实际发送基线请求

将实际记录映射到显式请求计划，按 `execution.md` 使用内置 replay.py 或已核实的 HTTP 客户端发送未修改请求，保存实际状态、响应头和相关完整响应体。原始 body 用 file/base64 保真，认证值通过账号环境来源注入。导出 curl、创建请求页或生成代码只表示准备完成。

保留编码、重复字段、表单顺序和签名语义；设置有限超时，不自动跟随范围未核实的重定向。保留原始 body 时使用文件或客户端的原始字节接口，避免 shell 插值改变请求或把 Token 暴露到日志。若任务要求重放也经过代理，为 HTTP 客户端显式设置已确认代理并在抓包记录中核对该次请求；不假设它沿用小程序代理。

账号 A/B 分别建立自己的业务基线与 Cookie 状态；一个账号失效只阻塞该账号。已有授权内可直接执行，不因工具选型重复索取授权。已知签名/加密格式才使用对应适配，未知格式保留 BLOCKED。

基线必须返回当前测试身份预期的业务结果。失败则区分证书、代理、会话、签名、参数或目标拒绝，写 BLOCKED/INCONCLUSIVE。不能声称已完成有效改参测试。

## 4. 形成并验证假设

从实际请求选择对象归属、租户隔离、功能授权、字段赋值、状态和重放等问题。先确认预期规则，再选最小单变量实验；两个账号只访问彼此授权的测试资源。允许的状态变更需有回滚，资金/竞态执行边界见 `safety.md`。

按 `replay.md` 构造请求，按 `dynamic-testing.md` 判断结果。响应 200、字段名称、错误差异或未触发 payload 均不足以确认漏洞或安全。

## 5. 交付实际结果

在 dynamic-test-results.json 中写 entry_mode 为 traffic 或 hypothesis，requests 保留已捕获/导入请求的来源、业务动作、身份、方法、URL、证据及 replay 状态。只有保存了实际发送和响应的证据才能写 replay.status=succeeded。

findings 保留具体实验结果，允许为空；requests 为空时明确说明抓包或输入阻塞，不能写“未发现问题”代替未完成。报告可以直接消费这份结果和 evidence.json，不要求补造源码路径或先跑静态阶段。

完成标准分别说明：抓到了哪些真实请求、哪些实际重放成功、哪些做了有效安全对照、哪些被阻塞。未得到测试目标或账号时只交付执行条件与限制，不编造流量或结果。
