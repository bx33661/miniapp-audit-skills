# 审计判断与证据

当选择验证方法、判断发现状态或记录覆盖时阅读。领域细节由对应阶段 reference 提供。

## 从主张到证据

每个候选写清：谁控制什么输入，本应保护什么资产，安全决策在哪里，观察到什么，以及哪条证据会推翻主张。客户端可传 `role`、`price` 或 `orderId` 只是输入事实；服务端是否错误信任它们需要验证。

源码不可见的部署配置、租户隔离、支付回调、代理或平台控制标为未知。测试失败可能来自签名、会话、WAF、参数或环境，不能直接证明授权有效。

## 信任边界

| 边界 | 需要核实的控制 |
|---|---|
| 小程序与微信平台 | 登录 code 的服务端交换、可信身份绑定、会话密钥的使用与暴露范围 |
| 客户端与后端 | 对象归属、租户、功能权限、价格计算与状态转换 |
| 客户端与云开发 | 云函数可信上下文、操作级授权、数据库和存储规则 |
| 后端与支付或第三方 | 回调身份、签名、金额、订单绑定、幂等与状态一致性 |
| web-view 与小程序 | 域名与跳转限制、消息结构及调用来源、桥接能力与敏感数据流 |
| 用户数据与处理者 | 实际收集时机、接收主体、告知同意、用途与必要性 |

不是所有问题都能归结为“后端缺鉴权”。公开包里的真实凭证、客户端提前收集数据等问题，应定位各自的暴露或处理边界。

## 证据等级与状态

| 等级 | 实际证明力 | 处理 |
|---|---|---|
| E0 | 关键字、模式或尚未追通的线索 | 观察项，不能确认 |
| E1 | 已定位路径和具体边界假设，但决定性事实未验证 | `needs_validation`，说明缺什么与如何验证 |
| E2 | 受控复现或可独立核验的直接证据，证明具体安全性质失效 | 满足发现契约后可 `confirmed` |
| E3 | 在授权测试数据上进一步证实影响范围或结果 | `confirmed`，影响限于实际证据 |

等级不按静态/动态工具划分。直接材料审查也必须证明具体失效；仅看到像密钥的字符串、危险函数或疑似缺失校验仍是 E0/E1。E2 已足够时停止，不为提高等级扩大影响。

有足够证据推翻原主张时用 `rejected`，写拒绝理由与证据。未触发、缺账号和环境受阻不能当作拒绝。候选可以有 `priority`；只有确认记录有 `severity`。发现 ID 使用稳定的 `F-001`，证据使用 `EV-001`，排序和合并不重编已有 ID。

动态实验的 `CONFIRMED / INCONCLUSIVE / BLOCKED / FALSE_POSITIVE` 是测试结果；只有通过发现质量门的 CONFIRMED 才成为最终 confirmed，INCONCLUSIVE/BLOCKED 保留待验证，FALSE_POSITIVE 在证据充分时映射 rejected。

## 覆盖与限制

对纳入范围的资产 × 测试类型 × 身份记录 `tested / partial / not_tested`。tested 和 partial 附证据引用；partial 和 not_tested 附原因与残余风险。资产或角色不在范围内时明确说明，不暗记已测。

材料缺失、未解析调用、签名阻塞、不可用账号和未核实配置是覆盖限制。数组为空只说明已执行检查未产生条目；未执行或未成功读取不能解释为零发现。会话 schema 保存覆盖记录，报告直接使用它，不根据发现数量推算覆盖率。

## 最小充分验证

先确认当前身份的正常基线，再单变量对照。越权使用两个授权账号和各自测试资源；资金或状态问题以独立可读的服务端结果为准。请求返回 200、错误文字变化或响应长度变化只是线索。

只记录能支撑主张的最少数据、实际输入和结果。未知外部前提保持未知。修复建议针对失效控制，复测描述具体请求或行为及通过条件，未复测不能写成已通过。
