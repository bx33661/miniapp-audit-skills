# 小程序审计方法论（Agent 版）

> 目标：把“找 pattern”升级为“证明信任边界失效”。
> 适用：微信小程序（原生 / uni-app / Taro / 云开发），黑盒 / 灰盒 / 白盒。
> 原则：只测授权目标；只做最小化验证；不访问他人数据；不执行破坏性写操作。

## 0. 核心命题

小程序前端代码可以被获取、反编译和修改，因此**客户端的一切都不可信**。
唯一可信的安全边界在**服务端**和**云函数**。

审计的核心问题不是“代码里有没有危险函数”，而是：

> **客户端可控的哪个字段，被服务端当成了可信输入？**

微信官方安全指引的三条底线：

1. 互不信任：不要信任用户提交的数据，校验必须放在后台。
2. 最小权限：代码、模块、云函数只拥有完成任务所需的最小权限。
3. 敏感数据不明文：AppSecret、密钥、身份证、手机号、银行卡不得明文出现在小程序文件中。
4. 重要业务逻辑放在后台或云函数；客户端代码只做展示和交互。
5. 后台接口与云函数必须做身份鉴权。

## 1. 审计循环

| 阶段 | 目标 | 关键产出 | 质量门 |
|---|---|---|---|
| 0 授权与范围 | 明确目标、账号、环境、时间、数据规则 | `scope.md` | 书面授权；生产只读；不碰他人数据；不执行支付/退款/删除 |
| 1 材料与资产 | 拿到完整代码、分包、插件、云环境、域名、SDK | `asset-inventory.json` | 主包/分包/插件齐全；版本一致；wxapkg 可解密；记录缺失项 |
| 2 业务建模 | 角色、资产、资金流、数据流、状态机 | `business-model.md` | 每个关键流程有正常路径、异常路径、滥用路径 |
| 3 信任边界与威胁建模 | 客户端/微信/后端/云/第三方之间的信任关系 | `threat-model.md` | 每个边界有 STRIDE 或 OWASP API Top 10 映射；有 abuse case |
| 4 静态验证 | 凭证、鉴权、签名、注入、WebView、云函数、供应链 | `findings.json`（E0/E1） | 每条发现含文件/行号/数据流；模式命中必须人工复核 |
| 5 动态验证 | 重放、改参、多账号、竞态、支付、重放攻击 | `dynamic-evidence.json`（E2/E3） | 可复现、最小化、可回滚；不写生产数据 |
| 6 证据与报告 | 归一化、去重、评级、修复建议 | `report.md` | 每个 CONFIRMED 发现通过质量门；E0/E1 只能进“待确认” |
| 7 复测与关闭 | 验证修复、回归、残余风险 | `retest.md` | 原 PoC 失效；同类接口不再复现；修复未引入新问题 |

**不要跳阶段。** 材料不全时先补材料；业务没建模时不要直接扫 pattern；没有 E2/E3 证据时不要把猜测写成漏洞。

## 2. 信任边界

| 边界 | 不可信的一方 | 必须验证什么 | 常见失败 |
|---|---|---|---|
| 小程序客户端 ↔ 微信平台 | 客户端 | `code2session` 结果、`openid/unionid`、`encryptedData/iv`、`session_key` 只在服务端使用 | 客户端传 `openid/userInfo` 当身份；`session_key` 下发前端；加密数据未验签/未解密校验 |
| 客户端 ↔ 自建后端 | 客户端 | 所有参数、Header、角色、价格、数量、状态、资源归属 | 只隐藏按钮不做服务端鉴权；IDOR/BOLA；价格/状态由客户端传入；过度返回字段 |
| 客户端 ↔ 云开发 | 客户端 | `cloud.getWXContext()` 的 `OPENID/APPID`；云函数内部再鉴权；数据库/存储规则 | 云函数合并 CRUD 无鉴权；数据库规则 `read/write: true`；env id/密钥泄漏；HTTP 触发器绕过 |
| 后端 ↔ 支付/第三方 | 第三方响应/回调 | 平台验签、金额一致性、订单状态、幂等、防重放 | 不验签；只信客户端 success；金额不校验；回调与对账逻辑不一致 |
| web-view ↔ 小程序 | 网页 URL / `postMessage` | 业务域名白名单；消息来源/结构；JSSDK 权限 | 用户可控 `src`；开放重定向；`postMessage` 未校验；JSBridge 越权调用 |

**每个发现都要回答：哪条边界失效了？** 如果答不出来，说明还没定位根因。

## 3. 六问透镜

对每个页面、接口、云函数、支付流程，依次问：

| 透镜 | 问题 | 小程序例子 | 验证方法 |
|---|---|---|---|
| Control | 谁能调用？ | 未登录接口、管理接口、云函数、HTTP 触发器 | 无 token/低权限 token 重放；多账号矩阵 |
| Input | 能传什么？ | SQL/NoSQL/命令/模板/路径/SSRF/富文本/文件上传 | Payload + 错误回显/时间盲注/带外 |
| State | 能改什么状态？ | 订单、支付、退款、优惠券、积分、库存、审核状态 | 状态机跳转；并发；越权状态变更 |
| Data | 能看什么数据？ | IDOR、过度返回、PII、日志、云存储文件 | 改 id/tenantId/unitCode；对比响应字段 |
| Money | 能占什么便宜？ | 价格、数量、折扣、券、积分、退款、邀请奖励 | 改金额/数量/券/并发；负数/小数/溢出 |
| Automation | 能重复什么？ | 重放、竞态、枚举、爬取、短信轰炸 | 并发/重放/速率/验证码复用 |

**优先级**：Money + Control 的组合通常最高；Data + Automation 可能形成拖库；State 问题常出现在支付/退款/审核。

## 4. 证据分级

| 等级 | 含义 | 能否写成“已确认” |
|---|---|---|
| E0 | 只看到模式/关键词，没有代码路径 | 否，最多“信息” |
| E1 | 静态代码路径 + 缺失校验，但未动态验证 | 否，写“待确认”，并给出验证步骤 |
| E2 | 动态重放/改参复现，响应符合漏洞判定 | 是，标 CONFIRMED |
| E3 | 进一步证明影响：拿到他人数据、改变资金/状态、绕过权限 | 是，标 CONFIRMED + 影响证据 |

**报告规则**：

- 只有 E2/E3 能进“已确认漏洞”。
- E1 必须写清楚“还缺哪一步验证”，不能夸大。
- E0 不进漏洞列表，最多进“观察项/覆盖说明”。
- 任何涉及他人数据的验证，必须使用测试账号/测试数据；拿到真实他人数据立即停止并脱敏。

## 5. 发现质量门

每个发现必须包含：

- 标题、严重性、置信度、CWE/OWASP 映射
- 受影响资产：endpoint / 云函数 / 页面 / 存储路径
- 前置条件：账号、角色、环境、必要配置
- 复现步骤：请求/响应（脱敏）、时间、账号角色
- 根因：哪条信任边界失效，服务端缺了什么校验
- 影响：数据、资金、权限、合规，尽量量化
- 修复建议：服务端/云函数修复，不是前端隐藏按钮
- 证据等级：E0–E3
- 覆盖与限制：没测什么，为什么
- 去重/关联：是否与其它发现构成利用链

**缺少任意一项，不进入正式报告。**

## 6. 覆盖矩阵

用矩阵记录“测了什么、没测什么”，不要用“已全面审计”这种无法验证的表述。

| 资产类型 \ 测试类型 | 认证 | 水平越权 | 垂直越权 | 输入校验 | 业务逻辑 | 重放/竞态 | 数据暴露 | 隐私 |

| HTTP API | T/P/N | T/P/N | T/P/N | T/P/N | T/P/N | T/P/N | T/P/N | T/P/N |

## 7. 小程序特有攻击面

### 7.1 登录与会话

- `wx.login` → `code` → 服务端 `code2session`；`openid/unionid` 只能在服务端使用。
- `session_key` 不得下发前端；`encryptedData/iv` 必须服务端解密并校验来源。
- 检查 token 存储位置、过期时间、刷新机制、注销后失效。
- 检查客户端传入的 `openid/userId/role/isAdmin` 是否被服务端直接信任。

### 7.2 云开发

- `wx.cloud.callFunction`：函数名、参数、调用者身份；云函数内部是否用 `cloud.getWXContext()` 鉴权。
- 云数据库：集合权限规则是否过宽；是否允许客户端直接读写敏感集合。
- 云存储：`cloud://` 文件 ID 是否可枚举；上传/下载权限是否按用户隔离。
- 云函数合并 CRUD：一个函数同时做增删改查，是否按操作类型分别鉴权。
- 云环境 ID、AppSecret、云密钥是否硬编码在客户端。

### 7.3 WebView / JSBridge

- `<web-view src>` 是否用户可控；业务域名白名单是否严格。
- `postMessage` 是否校验来源、结构、敏感操作；是否可被任意网页调用。
- JSSDK 的 `navigateTo/redirectTo` 是否可跳转到未授权页面。
- 是否存在开放重定向、XSS、钓鱼页面加载。

### 7.4 支付

- 客户端只传商品/数量/券 ID，金额由服务端计算；客户端传金额必须重新校验。
- `wx.requestPayment` 的 `prepay_id/paySign` 由服务端生成；商户密钥只在服务端。
- 支付结果以服务端异步通知为准，不能信客户端 `success`。
- 回调必须验签、验金额、验商户号/AppID、防重放、幂等。
- 订单状态机：客户端不能直接指定 `paid/refunded/shipped`。
- 退款、优惠券、积分、邀请奖励：检查并发、重复使用、负数/小数/溢出。

### 7.5 数据与隐私

- `requiredPrivateInfos`、`privacy` 配置与实际调用是否一致。
- 是否在用户同意前收集位置/手机号/相册/剪贴板。
- 本地存储是否保存 token/PII/密钥；是否明文。
- 第三方 SDK 是否收集数据、是否在隐私政策中披露。
- 用户注销/撤回授权后，服务端是否清理数据。

### 7.6 业务逻辑

- 价格、数量、折扣、券叠加、积分兑换、库存扣减、秒杀、抽奖、签到。
- 订单/支付/退款/审核状态跳转。
- 邀请/分享/裂变奖励的防刷。
- 分页/导出/搜索接口的批量数据获取。

### 7.7 供应链

- 插件、第三方 SDK、npm 依赖、云函数依赖。
- 是否引入已知漏洞版本；是否把密钥/内部地址打包进客户端。
- 第三方 API 的响应是否被无条件信任（OWASP API10）。

### 7.8 抗自动化

- 登录/短信/验证码/查询接口的速率限制。
- 枚举：自增 ID、手机号、订单号、学号/工号。
- 重放：sign/timestamp/nonce/session 绑定。
- 幂等：支付、退款、领券、下单。

## 9. 报告与复测

报告结构：

1. 审计信息：目标、版本、时间、范围、限制、授权。
2. 执行摘要：总体风险、发现统计、关键结论、修复优先级。
3. 业务与攻击面：角色、资产、接口、云函数、WebView、支付。
4. 覆盖矩阵：T/P/N + 未覆盖原因。
5. 安全发现：按严重性排序，每个发现过质量门。
6. 待确认项：E1 + 验证步骤。
7. 附录：API 清单、域名、SDK、证据索引。

复测标准：

- 原 PoC 不再复现。
- 同类接口/云函数不再复现，而不是只修一个点。
- 修复没有引入新的绕过（例如只加前端校验、只改返回码）。
- 回归测试通过，业务功能未破坏。
