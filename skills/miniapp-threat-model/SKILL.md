# 微信小程序威胁建模

## 目的

在测试前决定什么值得关注。没有业务模型的漏洞列表只会产生噪音；没有滥用用例的模型只会留下未验证的假设。

输出是一组有优先级的假设：哪些资产值得攻击，哪条信任边界在保护它，什么证据能证明失效。

## 建立模型

保持模型紧凑，不要写成完整文档。

- **资产。** 资金、个人信息、凭证、权限、库存、声誉、合规义务。
- **角色。** 匿名访客、普通用户、特权用户、管理员、服务账号。
- **流程。** 登录、浏览、搜索、下单、支付、退款、取消、分享、邀请、上传、导出、删除。
- **状态。** 订单、支付、退款、优惠券、积分、库存、审核、审批。
- **边界。** 客户端到微信平台、客户端到后端、客户端到云开发、后端到支付机构、web-view 到小程序。
- **标识。** `openid`、`unionid`、`userId`、`tenantId`、`unitCode`、`orderId`、`couponId`、`role`、`price`、`status`。

## 六问透镜

把透镜当作提问方式，不要机械地逐项打勾。

| 透镜 | 问题 | 典型证据 |
|---|---|---|
| Control | 谁能调用这个功能，如何强制？ | 未登录或低权限重放返回受保护数据或操作 |
| Input | 客户端能传什么，最终到哪里？ | 注入、模板、路径、SSRF、批量赋值、不安全文件处理 |
| State | 客户端能影响哪些状态转换？ | 订单在未授权情况下变为已支付、已退款或已发货 |
| Data | 客户端能读取哪些对象和字段？ | 对象级授权失效、过度返回、枚举 |
| Money | 价格、数量、折扣、积分或退款在哪里可被操纵？ | 服务端接受客户端计算的金额或不一致的总价 |
| Automation | 什么可以被重复、并发或枚举？ | 重放、竞态、暴力尝试、爬取、优惠券或奖励滥用 |

## 滥用用例

对每个关键流程写三条路径：

1. **正常路径。** 预期用户操作和服务端响应。
2. **异常路径。** 非法输入、过期状态、缺少权限、重复请求。
3. **滥用路径。** 同等或更低权限的攻击者如何获得数据、资金、权限或自动化优势。

一个好的滥用用例包含：

- 前置条件和所需账号。
- 客户端可控字段或操作。
- 本应存在的服务端校验。
- 证明失效的可观察信号。
- 确认所需的证据等级。

## 优先级

按以下因素排序：

- 业务影响：资金、个人信息、权限、合规风险。
- 可达性：未登录、普通用户、特权用户、仅内部。
- 证据成本：单请求、多账号矩阵、竞态窗口、逆向分析。
- 利用链：低影响发现是否能串联成更高影响。

不要在证据之前定严重性。假设可以有优先级，但不能被标成漏洞。

## 质量门

- 每个关键流程都有正常、异常和滥用路径。
- 每条信任边界至少有一个测试假设。
- 每个假设都写明客户端可控字段和待验证的服务端校验。
- 优先级由影响和可达性支撑。
- 未测试的流程和不可用角色记为限制。

## 输出

- 系统模型：资产、角色、流程、状态和边界。
- 滥用用例列表，包含前置条件和预期证据。
- 映射到静态和动态技能的优先测试计划。
- 覆盖限制。

## 安全边界

- 只对授权目标建模。
- 不设计需要他人数据的滥用用例；使用测试账号和合成标识。
- 假设必须标为假设，不能写成已确认发现。
