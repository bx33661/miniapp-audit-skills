# 鉴权与越权的验证决策

产物为 `evidence/authz-findings.json`，遵循 [authz-findings.schema.json](../assets/authz-findings.schema.json)，`skill` 为 `miniapp-static-audit`。结合 `evidence/attack-surface.json` 确定真实请求与身份来源，不按接口名或参数名直接定漏洞。

必需顶层为 `skill`、`scanned_at`、`source_dir`、`findings`、`limitations`；`findings[]` 使用 [finding.schema.json](../../miniapp-report/assets/finding.schema.json)，按状态填写其条件必需字段，不输出旧统计或自动风险分数。

## 识别服务端信任边界

- 追踪 `wx.login` 的 code 如何换取业务会话，服务端如何绑定 OpenID/UnionID、账号和租户。`wx.getUserProfile`、头像昵称或本地用户对象不证明业务认证成功。
- 核实 token/cookie 的来源、发送位置、会话绑定、过期和撤销。没有刷新接口或使用本地存储，不单独证明认证漏洞；小程序客户端是可控环境，服务端应独立作安全决策。
- 本地 `role`、`isVip`、`userId` 或页面显隐只能说明客户端行为。关键是服务端是否以可信身份作判断，是否错误信任可控字段。
- 云函数检查 `getWXContext` 的使用位置和运行语义，以及服务端身份是否被请求体同名字段覆盖。云数据库检查实际部署规则、集合归属字段及云函数的权限上下文。
- 小程序包未提供服务端源码、网关或云规则时，明确这些不可见范围；“客户端未见服务端校验”不能写成“服务端缺少校验”。

## 确定权限期望

为真正需要核实的资源建立最小权限对照：请求主体、资源所有者、租户、动作、预期允许范围及依据。业务规则未知就保留 `unknown`，不凭订单、管理员或 VIP 等词推测访问政策。

可将这些上下文写入 `auth_mechanism`、`identities`、`resources` 与 `matrix`。矩阵的预期与实际分别记录；没有执行的单元格不能填写实际允许或拒绝。不要生成大张空表。

| 边界问题 | 最小核实方式 | 能支持确认的观察 |
|---|---|---|
| 水平越权 | 授权测试账号 A/B 各拥有测试资源，仅替换资源 ID，其他上下文不变 | A 在业务应拒绝的场景读到 B 的受保护字段，或 B 的测试资源产生可核验变更 |
| 垂直越权 | 普通身份请求有明确权限要求的管理动作；确认高权限基线 | 普通身份实际完成受保护动作，不仅是出现管理页面或返回 200 |
| 租户隔离 | 同一角色、不同测试租户，对照租户绑定与资源归属 | 请求参数覆盖可信租户边界并获得越界结果 |
| 未认证访问 | 分别移除实际使用的会话、签名等认证材料，对照业务基线 | 未认证主体获得业务规定需认证的数据或操作权限 |
| 客户端角色信任 | 修改可控角色字段，同时保持可信身份不变 | 服务端权限实际随可控字段提升 |
| 会话失效 | 在测试会话退出/撤销后重放原会话，检查规则适用性 | 按约定应失效的会话仍能完成受保护动作 |

只使用授权账号和测试资源，不枚举真实用户 ID。写清方法、真实端点、改动字段、前置条件、预期与判定证据；敏感认证值用证据引用替代。403、401、200 或响应长度都不能独立代表权限结论，需核实内容和业务后置状态。

## 数据路径和保护判断

围绕可控来源、请求封装、服务端身份解析、资源查询条件及实际操作逐段记录。看到 `role`、`session`、`includes` 或“权限检查”函数名不证明保护有效；确认检查的对象、可信来源、执行时机、失败分支及每条到达路径。客户端 guard 不能替代服务端决策。

静态服务端实现也能提供可独立核验的直接证据，但必须建立可达性、身份来源和失效条件；不完整片段或关键词组合最多是待验证路径。

## 发现输出

- `findings[]` 使用统一 finding schema，稳定编号 `F-001`；不按排序重建编号，不另建 AUTHZ 编号体系。
- 明确 `status`：`needs_validation`、`confirmed` 或 `rejected`，无默认值或兼容别名。候选可有 `priority`，仅 `confirmed` 有 `severity`。
- E0 为线索；E1 为有根据的待验证路径；E2 为可复现或可独立核验的直接证据证明具体边界失效；E3 为在授权测试数据上进一步证实影响范围。等级不按静态/动态手段划分。
- 确认需 E2/E3、非空证据引用，并填写根因、复现、影响、修复、预期与实际、复测。被有效服务端边界排除的假设记 `rejected` 并保留依据。
- 数据路径放在 finding 的 `dataflow`，测试前置和步骤放在该 finding 支持的结构中，不新增平行测试文件或虚构已执行结果。
- 只有已确认发现进入最终风险计数。E2 已足以证明边界时停止扩展，不追求更大数据范围。
